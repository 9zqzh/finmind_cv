## 一、总览：一张图看懂系统组成

```text
浏览器（用户）
   │  http://localhost:5173
   ▼
前端（React + Vite + Ant Design）          ← front_end/web
   │  /api/* 请求经 Vite 开发代理转发
   ▼
后端（FastAPI + PydanticAI Agent）          ← back_end/backend
   ├── DeepSeek 大模型（OpenAI 兼容接口）   ← Agent 的"大脑"
   ├── gduf-jwxt-api（教务系统客户端）     ← PyPI 依赖
   ├── gduf-web-api（学院官网客户端）      ← PyPI 依赖
   ├── gduf-academic-api（学术资源客户端） ← back_end/gduf-academic-api
   └── 本地知识库文件（.md/.txt/.json）     ← data/knowledge、data/information
```

三个关键名词的通俗解释：

- **Agent（智能体）**：能"听懂"自然语言、自己决定调用哪个工具、再把结果组织成人类可读回答的程序。本项目的大模型是 DeepSeek，编排框架是 PydanticAI。
- **Tool Calling（工具调用）**：大模型本身不知道你的课表，它只能"决定"去调用哪个函数（如 `query_schedule`），真实数据由函数返回。
- **RAG（检索增强生成）**：先从本地资料里检索相关片段，再让大模型基于检索结果作答，避免模型"编造"。

### 2.3 PydanticAI 的使用方式（2.x 版本）

- **Agent 构建**（`app/agent/orchestrator.py`）：`Agent(model, deps_type=AgentDeps, system_prompt=...)`，全局单例懒加载。
- **工具注册**（`app/agent/tools.py`）：用 `@agent.tool` 装饰器注册 14 个工具；工具函数第一个参数是 `RunContext[AgentDeps]`，可访问会话、知识库等依赖。
- **依赖注入**：每次对话构造一个 `AgentDeps`（含当前用户会话、知识库、资讯库实例），通过 `agent.run(message, deps=deps)` 传入。
- **错误处理约定**：工具内部业务失败**不抛异常**，而是返回 `{"error": "..."}` 字典，让模型自己组织可操作的提示（如"请先登录"）。
- **两个版本坑**（已写入操作指南，新人务必注意）：
  1. PydanticAI 2.x 的异常模块**没有** `ToolError`，不要导入它；
  2. 不要用 `asyncio.wait_for` 包裹 `agent.run()`，会与框架内部任务图冲突导致假性超时，超时控制依赖 OpenAI 客户端自身的 timeout 参数。

### 2.4 DeepSeek 模型接入

- **接入方式**：OpenAI 兼容接口（不是 DeepSeek 专属 SDK），实现见 `app/agent/model_client.py`：

```python
client = AsyncOpenAI(base_url=settings.deepseek_base_url,
                     api_key=settings.deepseek_api_key,
                     timeout=settings.agent_timeout_seconds)
model = OpenAIChatModel(settings.deepseek_model,
                        provider=OpenAIProvider(openai_client=client))
```

- **模型名**：默认 `deepseek-v4-flash`（实测可用；`deepseek-chat` 同样可用）。换模型只改 `.env` 中的 `DEEPSEEK_MODEL`，不动代码。
- **好处**：将来换成任何 OpenAI 兼容服务，只需改 `DEEPSEEK_BASE_URL` 和模型名。

### 2.5 gduf-jwxt-api（教务系统客户端）

- **是什么**：PyPI 包 [`gduf-jwxt-api==0.2.0`](https://pypi.org/project/gduf-jwxt-api/)（导入名 `jwxtapi`），封装广东金融学院综合教务管理系统的登录与查询：验证码获取、学号密码登录、会话保持、个人课表、教室课表、成绩、成绩明细、培养方案、教学楼列表。
- **关键特点**：**同步** httpx 客户端，返回值是冻结 dataclass（可 `to_dict()`）；一套明确的 `JwxtError` 异常体系。
- **在本项目中的位置**：后端通过 `app/adapters/jwxt.py` 适配层调用它——用 `asyncio.to_thread` 把同步调用包装成异步，把它的异常统一映射为后端错误码。
- **安装方式**：已精确声明在 `back_end/backend/pyproject.toml`，安装后端时自动从 PyPI 安装。源码和 API 文档见[上游仓库](https://github.com/LiangJZ1/gduf-jwxt-api)。

### 2.6 gduf-web-api（学院官网与竞赛平台客户端）

- **是什么**：PyPI 包 [`gduf-web-api==0.2.1`](https://pypi.org/project/gduf-web-api/)（导入名 `gduf_web_api`），封装学院官网（https://ai.gduf.edu.cn/）的公开内容抓取与搜索（AI 搜索、文章详情、师资列表、新闻列表等），以及学院竞赛管理与问答平台（`aijspt`，ai-data-competitions.cn）的公开信息检索（比赛列表/详情、通知公告、竞赛社团）。
- **关键特点**：**同步** httpx 客户端，无需登录；返回值是冻结 dataclass（`ArticleSummary`/`PageResult`/`ListResult`/`CompetitionSummary`/`CompetitionDetail`/`Notice`/`ClubSummary` 等）；异常体系 `GdufError` > `NetworkError`/`ParseError`/`InvalidPageError`/`UnsupportedSourceError`；内部按来源适配器协议（`SourceAdapter`/`CompetitionSourceAdapter`）组织，新增来源不破坏既有 `get_ai_*`/`get_aijspt_*` 行为。
- **在本项目中的位置**：后端通过 `app/adapters/gduf_web.py` 适配层调用它——同样用 `asyncio.to_thread` 包装同步调用，异常映射为 `ApiError`。官网搜索（`search_website`）与竞赛平台四类查询（`query_competitions` 比赛列表、`query_competition_detail` 单场详情、`query_competition_notices` 通知公告、`query_competition_clubs` 竞赛社团）均已注册为 Agent 工具。模块级 `GdufClient` 懒加载复用。另：竞赛平台对无效 ID/URL 抛 `ValueError`，适配层在 `run_gduf` 中统一归一为 `INVALID_PARAM`。
- **安装方式**：已精确声明在 `back_end/backend/pyproject.toml`，安装后端时自动从 PyPI 安装。源码和 API 文档见[上游仓库](https://github.com/LiangJZ1/gduf-web-api)。

### 2.7 gduf-academic-api（学术资源客户端）

- **是什么**：项目自带的本地 Python 包（`back_end/gduf-academic-api`），聚合搜索 arXiv、Semantic Scholar 等开放学术平台的论文与文献资料。
- **关键特点**：**同步** httpx 客户端，无需登录；支持 `proxy` 参数配置代理；采用可扩展注册表架构，新增平台只需在 `platforms/` 目录下创建模块文件并用 `@register` 装饰；异常体系 `AcademicError` > `NetworkError`/`ParseError`/`ValidationError`/`UnsupportedPlatformError`。
- **在本项目中的位置**：后端通过 `app/adapters/academic.py` 适配层调用它——同样用 `asyncio.to_thread` 包装同步调用，异常映射为 `ApiError`。模块级 `AcademicClient` 懒加载复用。
- **安装方式**：可编辑安装 `pip install -e ../gduf-academic-api`。

## 四、数据与存储方案

原型阶段刻意不引入数据库，全部采用"文件 + 内存"的轻量方案：

### 4.1 知识库与资讯（文件存储 + 关键词检索）

- **数据格式**：`.md` / `.txt` / `.json`，分别放在 `back_end/backend/data/knowledge/`（制度流程、学院简介等）和 `data/information/`（学院资讯、竞赛信息）。
  > ⚠️ 当前两个目录里只有**示例数据，待替换**为真实学院资料。
- **检索方案**（`app/knowledge/service.py`）：启动时加载全部文件 → Markdown 按标题切片、超长段按 400 字符二次切分、JSON 按记录切片 → 检索时用**中文双字（bigram）+ 英数单词**做关键词评分（`得分 = 出现次数 × 词长度`），返回 top-k。
- **为什么不用向量数据库**：零额外依赖、零安装风险，一周原型够用。技术选型文档规划了升级路径：后续可换 ChromaDB + 中文 embedding，检索接口不变，只替换 `KnowledgeService` 内部实现。

### 4.2 会话管理（内存 + TTL 过期）

- **实现**（`app/services/session.py`）：`SessionManager` 用字典在内存中保存 `token → JwxtSession`。每个会话绑定一个独立的 `JwxtClient` 实例（独立 Cookie 与登录态，禁止全局共享）。登录用户的会话还支持多轮对话记忆（`chat_history: list[ChatTurn]`），滑动窗口保留最近 6 轮。
- **TTL 机制**：会话超过 `SESSION_TTL_MINUTES`（默认 120 分钟）未活动即过期销毁；token 用 `secrets.token_urlsafe(24)` 生成。
- **局限（待实现）**：内存方案在服务重启后会话丢失、不支持多进程部署。技术选型文档规划后续迁移 SQLite/Redis。

### 4.3 前端本地存储

仅用 `sessionStorage` 保存 `session_token`（关闭标签页即失效）；密码、验证码不落盘。

### 4.4 与规划文档的差异说明（以代码为准）

《技术选型与五人分工规划》4.2 节提到"SQLite + SQLAlchemy/SQLModel"，但**当前骨架未实现持久化存储**（无 `storage/` 目录），会话与成绩缓存均在内存中；这属于原型阶段有意的简化。

## 七、技术选型回顾：为什么是这套组合

1. **FastAPI + PydanticAI + Pydantic 全家桶**：类型一致贯穿请求校验、Agent 工具参数、响应模型，联调摩擦最小。
2. **OpenAI 兼容方式接 DeepSeek**：不绑定专有 SDK，模型/地址全可配置，随时可换服务商。
3. **关键词检索兜底而非向量库**：原型期零依赖风险；接口设计预留了升级位。
4. **内存会话而非数据库**：教务客户端实例必须与登录 Cookie 绑定，内存字典最简单直接；生产化再迁移。
5. **Vite 代理 + 统一 JSON 契约**：前端不碰跨域，后端只返回 `{success, data, message, code?}` 结构，双方按冻结的接口类型并行开发。
